**Feature Branch**: `001-rights-runtime-mvp`

**Created**: 2026-09-02

**Status**: Ready for Implementation（day1 probe 依存の未決事項 R-2 / R-4 / R-5 / R-7 は `plan.md` に隔離。09-04 の T018–T021 で確定）

**Input**: User description: "docs/idea.md §0–21（TrueCollective 企画書 / 要件定義書 v1.6）に基づく、ETHOnline 2026 向け MVP。Owner Epoch と Rights Receipt（License Epoch）を分離管理し、NFT 移転時にアクセス・ライセンス・将来収益をそれぞれ定義済みのルールで更新する transfer-coupled rights runtime。保護対象は暗号化された独占データセット、鍵配布はゲートウェイ分散鍵方式（KeyGate）、決済は x402 経由でオンチェーンに原子的にアンカーし、AI Agent が自律的に発見・購入・復号・分析まで行う。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 所有者は無料アクセスでき、NFT移転で即座に失効する (Priority: P1)

コレクター（NFT所有者）は、保有するNFTに紐づく暗号化コンテンツへ追加支払いなしでアクセスできる。NFTを他のウォレットへ譲渡すると、譲渡元は次にアクセスを試みた瞬間に拒否され、譲渡先は即座にアクセスできるようになる。コンテンツの暗号文自体は移転の前後で変わらない。

**Why this priority**: これがプロダクトの中心命題（Owner Epochによる所有者権限管理）そのものであり、これが機能しなければ他のどの機能も「Transfer-Coupled」を名乗れない。単独でも「所有権とアクセス権が同期するNFT」という価値を実演できる。

**Independent Test**: ウォレットAでNFTを保有した状態で復号・閲覧に成功させ、続けてウォレットBへNFTを移転し、Aの再アクセス試行が拒否され、Bの初回アクセスが成功することを確認するだけで完結する。他の機能（決済・AI Agent等）は不要。

**Acceptance Scenarios**:

1. **Given** ウォレットAがNFTを保有している, **When** Aが署名して復号鍵材料を要求する, **Then** Aは暗号化コンテンツを取得・復号・閲覧できる
2. **Given** ウォレットAがNFTをウォレットBへ移転済みで、Aが移転前に発行された所有者セッションを保持している, **When** Aがそのセッションでアクセスを試みる, **Then** アクセスは「セッションが移転をまたいで無効化された」を理由に即座に拒否され（`OWNER_EPOCH_MISMATCH`）、Aは再度の所有権確認を求められる
2a. **Given** ウォレットAがNFTをウォレットBへ移転済みである, **When** Aが有効なセッションを持たず新規に所有者アクセスを要求する, **Then** アクセスは「現在の所有者ではない」を理由に拒否される（`NOT_CURRENT_OWNER`）
3. **Given** ウォレットAがウォレットBへNFTを移転済みである, **When** Bが署名して初めてアクセスを要求する, **Then** Bは（Aの旧セッションとは無関係に）暗号化コンテンツを取得・復号・閲覧できる
4. **Given** NFTが移転された, **When** 移転前後で暗号化コンテンツ自体を比較する, **Then** 暗号文は変更・再暗号化されていない

### User Story 2 - 非所有者・AI Agentが有料アクセスを購入し、復号後に分析まで行う (Priority: P2)

NFTを所有していない第三者、または自律的に行動するAI Agentは、公開プレビューと利用条件を確認したうえで、期限・利用回数付きの有料アクセス権を購入する。支払いが確定すると同時に、購入者への利用権が発行され、作者と現在の所有者へ収益が分配される。AI Agentの場合は、復号したデータセットに対する分析的な質問に自律的に回答するところまでを人手を介さず完結できる。

**Why this priority**: x402による人間・AI双方への有料アクセス提供と収益分配は、ゴール2・4・5（§3.1）を直接証明する。P1の所有者フローが機能した上で初めて価値が出る、二番目に重要な独立した価値の単位。

**Independent Test**: 非所有者のクライアント（またはAI Agentクライアント）が、公開されている資産に対して支払いを行い、その一度の支払いから発行された利用権を使って（期限・回数内で）複数回コンテンツへアクセスできること、収益が定められた比率で分配されることを、P1のフローとは独立に確認できる。

**Acceptance Scenarios**:

1. **Given** 非所有者が保護コンテンツへアクセスしようとする, **When** 支払いをしていない, **Then** システムは価格と利用条件を提示し、支払いを要求する
2. **Given** 非所有者が価格・条件を確認した, **When** 定められた金額を支払う, **Then** 支払いの確定と同一の操作の中で、収益配分先（現在の所有者と作者）が確定・記録され、購入者に対して期限・利用回数付きの利用権が発行される
3. **Given** 購入者が有効な利用権を持っている, **When** 利用権の有効期限内・利用回数の上限内で複数回コンテンツへアクセスする, **Then** 各回とも復号に成功し、利用済み回数が正しく積み上がる
4. **Given** 購入者が利用権の利用回数上限に達した, **When** さらにアクセスを試みる, **Then** アクセスは拒否される
5. **Given** AI Agentが資産を発見し購入・復号まで完了した, **When** データセットに対する分析的な質問が投げかけられる, **Then** AI Agentは人手の介入なしに実際の推論により回答する
6. **Given** 収益分配が実行された, **When** 作者と現在の所有者の受取額を確認する, **Then** 設定された比率どおりで端数の扱いも一貫しており、合計に誤差がない

### User Story 3 - NFT移転時にライセンス種別ごとに異なる挙動を並べて示せる (Priority: P3)

作者は資産ごとに「購入済みライセンスがNFT移転後も存続するか、それとも失効するか」を設定できる。NFTが移転された瞬間、所有者の無料アクセスは即座に失効する一方で、存続設定のライセンスを持つ第三者はそのまま期限までアクセスを継続できる。失効設定のライセンスを持つ第三者は、移転後にアクセスしようとすると明確な理由とともに拒否される。

**Why this priority**: 「所有者権限」と「購入者権限」が別々の失効ルールで管理されているという、本プロダクトの中心的な発明（二層構造）を最も直接的に証明する。P1・P2が単体で動いた後、両者を組み合わせて見せる仕上げの価値。

**Independent Test**: 同一のNFT移転イベントに対して、(a) 旧所有者の無料アクセス失効、(b) 存続設定の第三者ライセンスの継続、(c) 失効設定の第三者ライセンスの拒否、の3つを個別に検証できる。それぞれ既存のセッション・利用権を使い回すだけで、新たな購入や移転を発生させずに確認可能。

**Acceptance Scenarios**:

1. **Given** 第三者が「移転後も存続する」設定の有料ライセンスを購入済みである, **When** 対象NFTが移転される, **Then** 当該ライセンスは有効期限まで引き続き利用できる
2. **Given** 第三者が「移転後は失効する」設定の有料ライセンスを購入済みである, **When** 対象NFTが移転される, **Then** 当該第三者が移転後にアクセスを試みると、専用の理由とともに明確に拒否される
3. **Given** NFTが移転された, **When** 旧所有者の無料アクセス失効・存続ライセンスの継続・失効ライセンスの拒否を同時に確認する, **Then** 3つの挙動がそれぞれ設定どおりに独立して観測できる

---

### User Story 4 - 不正利用・攻撃の試行はすべて安全に拒否される (Priority: P4)

悪意のある第三者や誤動作したクライアントが、利用権の使い回し（リプレイ）、別リソースへの転用、並行した多重利用、期限切れ利用権の利用、支払い不足などを試みても、システムはそれぞれを想定どおりのエラーで一貫して拒否する。とりわけ同一利用権に対する大量の同時アクセス試行では、成功はちょうど1回のみに限られる。

**Why this priority**: セキュリティ・堅牢性の証明はP1〜P3が成立した後に初めて意味を持つ検証レイヤーであり、機能そのものではなく機能の信頼性を担保する。ハッカソンの評価・デモ上は重要度が高いが、独立した「ユーザー価値」の単位としては最も後段。

**Independent Test**: 正当な利用権・セッションを一つ用意した状態で、上記の不正操作パターンをそれぞれ個別に試行し、期待される拒否理由が返ることを確認できる。新たな正常系フローの実行は不要。

**Acceptance Scenarios**:

1. **Given** 既に一度消費された利用権がある, **When** 同じ利用権を再度使おうとする, **Then** 「利用済み」を理由に拒否される
2. **Given** 有効な利用権がある, **When** 同一の利用権に対して20件の同時アクセスが試みられる, **Then** アプリ層で19件が「利用済み」を理由に3秒以内に拒否され、成功候補の1件はオンチェーンの消費操作の確定をもって確定し、最終的に成功はちょうど1件に限られる
3. **Given** ある資産向けに発行された利用権がある, **When** それを別の資産へのアクセスに使おうとする, **Then** 「対象リソース不一致」を理由に拒否される
4. **Given** 利用条件が事後に改ざんされた, **When** 改ざん後の条件でアクセスしようとする, **Then** 「条件不一致」を理由に拒否される
5. **Given** 利用権の有効期限が切れている, **When** それでもアクセスしようとする, **Then** 「期限切れ」を理由に拒否される
6. **Given** 必要額に満たない支払いが行われた, **When** 支払いを確定しようとする, **Then** 支払いは確定されず、利用権も発行されない
7. **Given** 別のウォレットが利用権の権利者になりすまそうとする, **When** アクセスを試みる, **Then** 「権利者不一致」を理由に拒否される

### Edge Cases

- 支払いが確定した直後にクライアント側の復号処理が失敗した場合の扱い：**決定**——利用回数を確定させる消費操作（`consume`）がオンチェーンで確定していれば、利用回数は消費済みとして確定する（settle-before-release の帰結）。ただし `consume` が確定済みで、鍵材料（`share_G`）の *配信のみ* が失敗した場合に限り、同一の利用回数インデックス（`useIndex`）に対する鍵材料の再取得を一定時間内（既定：5分）許容する。返金・クレジット再発行は行わない（Assumptions）。
- **鍵材料発行サービスが一時的に応答不能**：**決定**——MVP では代替経路を設けない。Access Gateway の可用性は単一障害点であり、この前提を提出 README（T123）で開示する。production は複数リージョン化 / `share_U` の Shamir 2-of-3 分散（stretch）で緩和する。
- **同一 `paymentId` に内容の異なる支払いリクエスト**：**決定**——最初に受理された `(paymentId, purchaseRequestHash)` の組が有効で、異なる body の再送は `PAYMENT_ID_PAYLOAD_CONFLICT` で拒否する（FR-017、`UNIQUE(payment_id, purchase_request_hash)`）。
- **所有者がコントラクトウォレット（マルチシグ等）**：**決定**——本MVPの範囲外（FR-025）。`ownerOf` / `licensee` がコード付きアドレスの場合は `CONTRACT_WALLET_UNSUPPORTED` を返し、対応ウォレット種別（EOA 相当のみ）を README に明記する。
- **有料ライセンス発行後にポリシーが更新（緊急失効を含む）された**：**決定**——`bumpLicenseEpoch` で `licenseEpoch` を更新し、以降 旧 `licenseEpoch` の利用権は `LICENSE_EPOCH_MISMATCH` で拒否される（FR-011 の運用面、`contracts/error-codes.md` #14）。確定済みの収益配分は遡及変更しない（FR-010）。
- **NFT移転時に発行済み利用権が大量に存在**：**決定**——移転は `licenseEpoch` に触れないため、`SURVIVE_TRANSFER` の利用権はすべて継続、`INVALIDATE_ON_TRANSFER` はすべて `hasValidConsumption` の世代判定で一括拒否される。デモ規模（利用権 数十件）での正しさを US3 の契約テスト（`RightsRegistry.transferMode.spec.ts`、T035）で検証する。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: システムは、各NFTごとに所有者権限の世代（Owner Epoch）を保持し、NFTが移転されるたびにこの世代を自動的に更新しなければならない（MUST）。更新の主体はNFTを管理するコントラクト自身に限られ、外部の監視サービスがこの値を書き換えてはならない（MUST NOT）。
- **FR-002**: システムは、所有者に対する無料アクセスの許可判定を、判定の都度、その時点でのオンチェーンの所有権・世代情報を直接読み取って行わなければならない（MUST）。過去に発行されたセッション情報や外部インデックスの値だけで判定してはならない（MUST NOT）。所有者セッション（UX 用の短命クレデンシャル）は発行時点の所有者権限世代（`accessEpoch`）を保持してよいが、これは表示・エラー選択のためのメタデータに過ぎず、認可の根拠にしてはならない（MUST NOT）。
- **FR-003**: NFTが移転された場合、旧所有者の無料アクセスは次回のアクセス試行時に即座に拒否され、新所有者の無料アクセスは即座に許可されなければならない（MUST）。旧所有者の拒否理由は次のとおり切り分けられなければならない（MUST）：(a) 移転前に発行された所有者セッションを提示してのアクセスは「セッションが移転をまたいで無効化された」を理由に拒否する（`OWNER_EPOCH_MISMATCH`）。(b) 有効なセッションを持たない主体が新規に所有者アクセスを要求し、現在の所有者と一致しない場合は「現在の所有者ではない」を理由に拒否する（`NOT_CURRENT_OWNER`）。(a) と (b) がともに成立する場合は (a) を優先して返す。
- **FR-004**: システムは、非所有者・AI Agentに対して、保護コンテンツごとの価格・利用条件（期間・利用回数・商用利用可否・AI学習可否・二次生成可否を含む）を機械可読な形式で提示しなければならない（MUST）。
- **FR-005**: 非所有者・AI Agentは、提示された価格を対象チェーンのネイティブトークン（Hedera Testnet の HBAR）で x402 決済することで、期限・利用回数付きの利用権（Rights Receipt）を取得できなければならない（MUST）。
- **FR-006**: 発行される利用権は、少なくとも次の値に暗号的に束縛されなければならない（MUST）：対象チェーン、対象コントラクト、対象NFT（コントラクト＋トークンID）、対象リソース、対象条件、ライセンス世代、**発行時点の所有者権限世代**、権利者、許可された用途、**移転時の挙動種別**、利用回数上限、有効期限、購入行為そのもの、支払いID、one-timeな識別子、**発行時刻**。この全17フィールドの EIP-712 struct hash を利用権の識別子（`receiptHash`）とし、オンチェーンの権利認可の権威とする。利用権は別リクエスト・別リソース・別条件へ転用できてはならない（MUST NOT）。なお「発行時点の所有者権限世代」は監査用メタデータであり、「移転後も存続する」設定の利用権の検証では現在の所有者権限世代との一致を要求してはならない（MUST NOT。FR-012）。
- **FR-007**: 1件の利用権は、その有効期限・利用回数上限の範囲内で複数回の利用を許可できなければならない（MUST）。個々の利用（アクセス）は、購入行為そのものではなく、サーバが管理する厳密に増加する利用回数カウンタによって区別されなければならない（MUST）。ある利用回数インデックスについて消費操作がオンチェーンで確定済みで、鍵材料の *配信のみ* が失敗した場合、システムは同一の利用回数インデックスに対する鍵材料の再送を一定時間内で許容してよい（MAY）。この際、新たな消費操作を発生させてはならない（MUST NOT）。
- **FR-008**: システムは、支払いの確定と、収益配分先の確定・記録、利用権の発行を、一つの不可分な操作の中で行わなければならない（MUST）。支払いが確定しなかった場合、利用権は発行されてはならない（MUST NOT）。この原子性が技術的に成立しない構成へやむを得ず変更する場合に *限り*、決済された資金を常にコントラクトの管理下に置いたまま、誰でも呼べる確定処理で収益配分先の記録と利用権の発行を行う方式へ切り替え、決済と発行が非原子である旨を提出物（README）に開示しなければならない（MUST）。これは既定の設計ではなくフォールバックである（憲章セキュリティ節と同一条件）。
- **FR-009**: 収益配分先（現在の所有者）は、支払いが確定した時点でのオンチェーンの所有権情報に基づき、その場で不可逆に確定・記録されなければならない（MUST）。事後の残高引き出し操作は、この確定済みの記録を払い出すのみとし、所有者情報を再度解決してはならない（MUST NOT）。
- **FR-010**: 一度確定した収益配分の記録は、その後にNFTが再度移転されても遡及的に変更されてはならない（MUST NOT）。
- **FR-011**: 作者は、資産ごとに「購入済みライセンスがNFT移転後も存続するか、失効するか」を設定できなければならない（MUST）。
- **FR-012**: 「移転後も存続する」設定の有料ライセンスは、NFTが移転されても、当該ライセンス自身の有効期限・利用回数上限の範囲内で利用可能でなければならない（MUST）。この判定にNFTの現在の所有者権限世代との一致を要求してはならない（MUST NOT）。
- **FR-013**: 「移転後は失効する」設定の有料ライセンスは、NFTが移転された後にアクセスが試みられた場合、所有者権限の世代不一致とは別の、専用の明確な理由で拒否されなければならない（MUST）。
- **FR-014**: システムは、保護コンテンツの本体を暗号化した状態でのみ保管しなければならない（MUST）。平文コンテンツ・復号に必要な完全な鍵材料をオンチェーンや恒久的な形で外部に公開してはならない（MUST NEVER）。
- **FR-015**: 復号に必要な鍵材料は、アクセス判定に合格した都度、その時点でのオンチェーンの権利状態に基づいて発行されなければならない（MUST）。NFTの移転が発生しても、暗号化コンテンツ本体の再暗号化・再アップロードを必要としてはならない（MUST NOT）。
- **FR-016**: 復号を仲介する側（ゲートウェイ）は、単独では平文コンテンツにも復号に必要な完全な鍵材料にもアクセスできない構成でなければならない（MUST NOT）。実際の復号処理は、アクセス主体のクライアント側で完結しなければならない（MUST）。
- **FR-017**: システムは、以下を含む不正利用の試行それぞれに対して、専用の識別可能な理由とともにアクセスを拒否しなければならない（MUST）：利用済み利用権の再利用、別リソースへの利用権の転用、改ざんされた利用条件での利用、期限切れの利用権の利用、利用回数上限を超えた利用、権利者と異なる主体による利用、支払い不足、同一支払いIDに対する内容不一致の再送、失効した所有者セッションでの利用。
- **FR-018**: 同一の利用権・利用回数の組み合わせに対して多数のアクセスが同時に試みられた場合、システムは成功をちょうど1件のみに限定し、残りすべてを一貫した理由で拒否しなければならない（MUST）。

### Key Entities

- **RightsNFT（権利付きNFT）**: 保護対象コンテンツと紐づく所有権の単位。所有者権限の世代（Owner Epoch）を持ち、移転のたびにこの世代が更新される。
- **Rights Manifest（権利マニフェスト）**: 資産ごとの、価格・利用条件・移転時の挙動・収益配分比率を機械可読に定義した情報。
- **Rights Receipt（利用権）**: 購入という行為に紐づく、期限・利用回数付きの具体的な利用許可。ライセンス世代（License Epoch）を持ち、所有者権限の世代とは独立して失効・更新される。
- **Encrypted Content Asset（保護コンテンツ資産）**: 暗号化された状態で保管される保護対象の本体（本MVPでは独占データセット）と、非保護の公開プレビュー。
- **Revenue Allocation（収益配分記録）**: 支払い確定時点で不可逆に確定される、作者・現在の所有者への配分額の記録。
- **Access Gateway（アクセス仲介）**: アクセス判定・支払い検証・利用権発行・復号鍵材料の放出可否判定を担う、部分的にのみ信頼される仲介者。
- **Creator（作者）**: 資産を発行し、継続的な収益を得る主体。
- **Owner / Collector（所有者）**: NFTを保有し、無料アクセスと将来収益の両方を得る主体。
- **Non-owner / AI Agent（非所有者・AIエージェント）**: 有料でアクセス権を購入する第三者。人間、またはシステムが公開する MCP サーバーへ接続して自律的に行動する外部 AI クライアント（Claude Code・Codex 等）のいずれか。**システムは自律実行体そのものを内包しない**——MCP ツールを提供し、自律ループは接続クライアントが担う。`agent/` パッケージは CI 用の検証ハーネスであり本番の実行体ではない。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 所有者は、ウォレット接続からコンテンツの復号表示まで（人が署名にかける時間を除く実処理時間）、中央値8秒未満・95パーセンタイル15秒未満で完了できる。
- **SC-002**: 非所有者・AI Agentは、支払い開始からコンテンツの復号表示まで、中央値20秒未満・95パーセンタイル40秒未満で完了できる。
- **SC-003**: NFTが移転された場合、旧所有者の次回アクセス試行（移転が確定してから最初の1回）で、10秒以内に失効が反映される。
- **SC-004**: 想定される不正利用・攻撃パターン全件（`contracts/error-codes.md` の14行 ＝ 拒否13種 ＋ 正常系1件：`SURVIVE_TRANSFER` 利用権が移転後も拒否されないことの確認）について、期待される結果が一致し、想定外の形での突破が0件である。
- **SC-005**: 同一利用権への20件同時アクセスにおいて、アプリ層（並行制御）で19件が「利用済み」を理由に3秒以内に一貫して拒否される。成功候補の1件はオンチェーンの消費操作の確定（Hedera finality 3〜5秒）をもって確定し、オンチェーン上でも消費操作は1件のみ成立する（コントラクト層の20件並行は別途検証する）。
- **SC-006**: 収益配分において、作者・現在の所有者の受取額が設定比率どおりとなり、端数を含めて合計の誤差が0である。
- **SC-007**: AI Agentが、資産の発見から支払い・復号・分析回答までの一連を、人の介入なしに完了できる。
- **SC-008**: 所有者がコンテンツにアクセスするまでに要する操作（ウォレット接続を含む）が3クリック以内である。
- **SC-009**: デモの中核となる経路（所有権確認、支払い確定、利用権の発行・検証、復号鍵材料の放出判定、AI Agentによる分析）が、模擬応答やハードコードされた結果ではなく、実際のインフラに対して動作する。
- **SC-010**: 想定される不正利用・攻撃パターン全件と、所有者・購入者・移転の主要な正常系シナリオについて、自動化された検証手段が存在する。API レイヤーについては Postman コレクションを Newman で実行する契約テストを含み、各レスポンスが OpenAPI 定義のスキーマに適合する。
- **SC-011**: MCPサーバー経由の決済ウォレットは、ポリシーで定めたセッション支出上限を超える支出、および許可されていないコントラクト・メソッドの呼び出しを試みても、いずれも拒否される。
- **SC-012**: Access Gateway の API の形をフロントエンドとバックエンドで食い違わせる変更（片方だけの手書き修正など）は、共通の生成型に対する型エラーとしてビルド時に検出される。

## Assumptions

- 保護対象の暗号化コンテンツはクライアント側で暗号化され、暗号化ストレージへ保管される。復号もクライアント側で行われ、仲介者は平文を扱わない。
- 所有者・購入者のウォレットは、決定的な署名が行える標準的な鍵ペア方式（EOA相当）であることを前提とし、コントラクトウォレット（マルチシグ等）は本MVPの対象外とする。
- デモ用の保護コンテンツ資産は、1ファイルあたり一定サイズ以下の独占データセット2種類とし、そのうち1種類は別の資産の利用権では開けないことを示すために使う。
- 決済に用いる資産は**対象チェーンのネイティブトークン（Hedera Testnet の HBAR）**とする。理由：Hedera「AI & Agentic Payments」トラックで必須の Blocky402 facilitator（`https://api.testnet.blocky402.com`）が `hedera:testnet` / `exact` スキームでサポートするのはネイティブトークンであり、HTS の USDC（`0.0.429274`）ではない（`/supported` 応答による）。価格・受取額・claimable 残高はすべて HBAR（EVM の `msg.value` 単位 ＝ weibar、10^18 = 1 HBAR。オンチェーンの精度下限は tinybar ＝ 10^8 なので金額は 10^10 weibar の倍数）で表す。詳細は `plan.md` / `research.md` R-2・R-4。
- 対象ネットワークは単一のチェーンとし、複数チェーンへの同時対応は本MVPの範囲外とする。
- 収益分配は作者と現在の所有者の2者構成に限定し、コミュニティ・プロトコル手数料等の追加の分配先は本MVPでは扱わない。
- 支払いに失敗した場合の返金・クレジット再発行の経路は、本MVPでは設けない（支払い自体が確定しない形で失敗を扱う）。
- 匿名所有証明（ZK）・複数チェーン対応・汎用マーケットプレイス・複数ライセンス種別（ERC-1155等）・完全なコピー防止（DRM）・法的著作権の自動移転は、本MVPの範囲外とする。
- Access Gateway の HTTP API は OpenAPI 3.1 定義（`packages/openapi/openapi.yaml`）を単一の真実源とし、`openapi-typescript` で生成した型をバックエンド・フロントエンド・エージェント経路が共有する。API レイヤーの E2E は Postman コレクション + Newman（`apps/e2e/postman/`）で行い、CI とデモ前チェックの双方で実デプロイに対して実行する（FR-029 / SC-010 / SC-012）。
- AI Agent向けのMCPサーバーは、Access Gatewayと同一のCloudflare Workers上でリモートホストし、Streamable HTTP/SSE経由で公開する。x402決済に用いるウォレットは、生の秘密鍵を仲介者が保持しないサーバーサイド署名方式（Privy server wallet の session signer）で管理し、「1セッションあたりの支出上限（HBAR 建て）」「呼び出し可能なコントラクト・メソッドのallowlist（`RightsRegistry` の決済関数のみ。ネイティブトークン決済のためトークン承認は不要）」「レート制限」を持つポリシーで制約する（FR-028）。公開エンドポイントへ到達できるクライアントでも、ポリシー上限を超えてテストネット HBAR を支出することはできない。デモ用に最小残高のみを保持する。

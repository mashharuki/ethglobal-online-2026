## 4. メッセージと3分デモ案

短い説明の候補：

> Transfer the NFT. Keep eligible paid access valid. Route future revenue to the new owner.

冒頭の問題設定：データ事業の管理者が変わるとき、既存顧客の購入済みアクセスを壊さず、旧管理者の無料アクセスと今後の売上だけを切り替えたい。

| 時間 | 見せること |
|---|---|
| 0:00〜0:12 | 問題と、旧Owner・新Owner・購入者の3者 |
| 0:12〜0:35 | 対象データ、購入済Receipt、移転前の状態 |
| 0:35〜1:20 | NFT移転と、旧Owner拒否・新Owner成功・同一SURVIVE Receipt成功 |
| 1:20〜2:00 | MCPエージェントによる新規購入→復号→具体的なデータの問いへの回答 |
| 2:00〜2:25 | 新規購入のCreator／新Owner配賦と、過去の配賦が不変であること |
| 2:25〜2:45 | 実証済みの攻撃拒否を1つ。二層epoch、Hedera、Privyの役割を短く説明 |
| 2:45〜3:00 | 利用先・公開URL・制約を一言 |

この順番は提案であり、実測済みであるとの主張ではない。5分期限のReceiptを使用する場合は、購入から移転後検証までを期限内に完了し、同じReceiptであることを追跡する。

## 5. 正確さを保つポイント

- 旧Ownerの拒否が署名不正や期限切れに起因すると、移転による失効の証明にならない。移転前に成功した有効なセッションを使い、拒否理由を確認する。
- SURVIVEを示す際は移転後に再購入しない。同一Receipt、licenseEpoch、期限、残回数を示す。
- 実決済railがcustodialなら、決済とReceipt記録全体を単一Txで原子的だと表現しない。
- Privy signer/quorumの署名要求者制御と、Gatewayが強制する支出額制限を区別する。README.md「Trust model」節の "MCP wallet" 項目に現時点の確認範囲が記載されている。
- 復号済みデータの回収や法的著作権の移転は主張しない。停止するのは以後のGatewayアクセス。
- 20並列デモはReceipt残回数とリクエスト内容に応じて期待値を定義する。「必ず1成功19拒否」と無条件に言わない。
